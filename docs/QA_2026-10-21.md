## Google TV virtual keyboard interaction, 2026-10-21 09:10 EDT

- User reported that the Google TV on-screen keyboard did not respond to mouse clicks while on Google's sign-in form.
- `dumpsys input_method` confirmed installed Google TV LatinIME (`com.google.android.inputmethod.latin/...LatinIME`), `mInputShown=true`, and the WebView was the IME served view. Keyboard was visibly open with focus on Q.
- **Verified keyboard D-pad input works:** injecting DPAD_RIGHT moved the highlighted key from Q to W, and DPAD_CENTER inserted a harmless single W into the focused text field; DEL removed it. The sign-in form was left blank. No credentials were entered or submitted by the assistant.
- **Verified touch/tap input did not:** Android `input tap` on the visible W key did not type it, matching the user's mouse-click complaint. This OS-provided Google TV keyboard appears to be remote-navigation-oriented rather than touch-operated.
- AVD configuration includes `hw.keyboard = yes`. Synthetic Windows SendKeys/native keybd_event attempts with the emulator foreground did not demonstrably navigate or type. **Human physical laptop keyboard typing has not been verified**, so do not claim it works. Android Emulator offers a Settings > General option for routing emulator keyboard shortcuts to the virtual device, but that option is not yet verified on this AVD.
- A clickable on-screen keyboard would likely require testing a separately installed, pointer-compatible IME on the disposable TV emulator; this is not a WebView webpage change. Do not replace the Google TV system keyboard without ensuring a recoverable fallback; do not handle passwords via ADB shell automation.
- All temporary screenshot captures and Windows key-injection test scripts should be removed once diagnostic checks are complete. No screenshot or credential should be committed.

## Google account sign-in field + TV remote conflict — 2026-10-21

**Report:** During Google sign-in inside the fal.ai WebView, Google TV's keyboard accepted remote D-pad letter selection and displayed the entered email, but the keyboard's submit arrow, and Google's Next button after dismissing the IME, did not progress. The email input's floating label visually overlapped part of the value. This is an incomplete/blocked login, not proof that the account credentials are invalid.

**Read-only diagnosis (personal fields redacted):** In the live `accounts.google.com/v3/signin/identifier` document the email field's DOM `value` was nonempty and the `Next` HTML button was present, visible and enabled. We deliberately did not read, log, save, or submit the actual email. The original Android app `MainActivity.dispatchKeyEvent` intercepted D-pad, Center, and Enter in every host and context, so browser-owned navigation and keyboard key handling were not properly prioritized.

**Code correction, built but not installed:**
- Let Android handle all key events when the IME is visible (WindowInsets + old-Android visible-frame fallback).
- Use native WebView input/focus for external login domains including Google and the fal authentication service; never inject custom JS navigation or synthetic WebView touches there.
- Show the custom TV cursor and focus modes only on fal's normal site pages; update overlay state when pages navigate.
- Preserve cookies and existing application data. No password handling, request rewriting, or user-agent spoofing.

**Status:** Kotlin Debug APK build passes; on-device regression tests still required. Reinstalling with `adb install -r` preserves application storage but restarts the process and may lose **unsent form text**; wait for user approval before replacing the running build. After replacement, have user re-enter email locally and verify native TV keyboard send and actual Google Next button, then record separate outcome for the overlapping floating label. If it still fails, distinguish Google embedded-WebView restrictions from incorrect IME event propagation; don't mask or spoof a prohibited OAuth client.
